# Threat Model

> **In short:** Profile's assets, trust boundaries, control register and accepted gaps.

Profile holds the personal data that describes people, so its first duty is that the data is seen only by those the person allows, and is truly gone when it is erased. This register follows the platform's Security standard, which replaced the Data Store Security Standard v0.1, and ADR-0006 ([resources](../RESOURCES.md)).

## 1. Assets

- Each person's attributes: names, contact details, locale and time zone.
- The names kept for leavers, and their pseudonyms.
- Each person's data key, and the host's wrapping keys.
- The disclosure settings, which say who may see what.

## 2. Trust boundaries

| Boundary | Trusted input | Untrusted input |
|---|---|---|
| Browser → host → Profile | The signed-in principal, from the host's subject resolver | Every identifier and value in a request, and its origin |
| Host's directory → host → Profile | The disclosure-context answer and Profile's commands, parsed strictly before use | — |
| Host → Profile's request parts | The part declaration in `composeProfile`, checked at composition | Any part named in a request, hold or report, checked against the declaration |
| Profile → key service | The wrapped key and its version | — |
| Host → database | Profile's schema, through a runtime role that owns nothing | Other capabilities' schemas (never read) |
| Host → Profile's clock | The current time, from the clock the host composes in server code (or the system clock) | Any time in a request |

## 3. Control register

| ID | Threat | Control | Evidence | Status |
|---|---|---|---|---|
| T1 | A viewer sees an attribute the person did not disclose to them | Per-attribute audience chosen by the person; secure defaults (name to group, all else to nobody); rules as pure functions over the disclosure context's relationship; unknown relationship or standing fails closed | `tests/disclosure.test.ts`; `tests/database.test.ts` "discloses each attribute" | Implemented |
| T2 | A paused, suspended or closing person is shown | Standing from the disclosure context at every lookup, never cached; paused hidden from listings but attributed; suspended, closing and gone hidden; in a group context, the subject's own membership there makes the standing stricter (`standingInGroup`) | disclosure and database tests | Implemented |
| T3 | Stale or partial disclosure when the host's directory fails | The port's answer is parsed; a rejection or malformed answer refuses the whole lookup (`unavailable`) | "fails closed when the disclosure-context port fails" | Implemented |
| T4 | Personal data read from the database, a dump or a backup | Every value encrypted with the person's own key (AES-256-GCM, fresh nonce, identity and purpose bound as AAD); keys stored only wrapped by the host's versioned key; no plaintext in records or outbox | "keeps every value encrypted"; `tests/keys.test.ts` | Implemented |
| T5 | Erased data survives in backups | Erasure deletes the wrapped key; wrapping-key rotation re-wraps live keys only; retiring the old version makes erased people's backed-up data unreadable | "rotates the wrapping key" | Implemented (host retires versions per its backup retention) |
| T6 | A record recreated for an erased person by a replayed or late command | Erased identifiers are recorded; provisioning and updates refuse them | "rotates the wrapping key" (erasure part) | Implemented |
| T7 | A ciphertext or wrapped key moved to another person | AAD binds identity and purpose; the wrapper binds identity | `tests/keys.test.ts` | Implemented |
| T8 | Personal data in events, logs or errors | Events carry identifiers, attribute names and codes only (schema-checked); validation errors carry problem codes; no value is logged | `tests/contracts.test.ts` | Implemented |
| T9 | Enumeration of people or records | A hidden display name is the same whether or not the person or record exists; `forbidden` is coarse | disclosure tests | Implemented |
| T10 | Spoofed or confusing names | Safe names: NFC, no control, format or private-use characters, no mixed scripts | `tests/contracts.test.ts` "Attributes" | Implemented |
| T11 | Contact details used before they are proven, or verified by someone who does not receive messages there | Stored unverified; a one-time code sent through the host's notifier, 6 digits, 10 minutes, 5 attempts, 5 sends an hour; kept only as an HMAC under the person's own key bound to the value, so a code never verifies another value and dies with the key; verification lapses when the value changes; sending needs a recent sign-in; Profile sends nothing else | `tests/http.test.ts` "verifies a contact detail", "spends a code" | Implemented (phase 4) |
| T12 | The runtime role alters the schema or deletes erasure records | Migrations run as the owner; the runtime role gets data access to its tables only, insert-only on `erased`, no ownership, no BYPASSRLS | "applies every migration once" | Implemented |
| T13 | A lost, repeated or reordered command or event leaves Profile inconsistent | Profile's commands are strict and idempotent by `commandId`, recorded in the same transaction as their effect and outbox writes; records created on first use if provisioning is late; Profile's own events in a transactional outbox, relayed in order, at least once | `tests/database.test.ts` "creates an empty record", "completes the directory part", "disposes of a deleted group" | Implemented |
| T14 | A missing port leads to an implicit store or key | Required ports fail closed (`ProfileCompositionError`) | `tests/composition.test.ts` | Implemented |
| T15 | A key service failure exposes or loses data | Wrap and unwrap failures refuse the operation (`unavailable`) | "fails closed when the key port fails" | Implemented |
| T17 | Acting on someone else's profile by naming them in a request | Endpoints take the person only from the subject resolver; strict bodies refuse unknown fields such as `subjectId` | `tests/http.test.ts` "takes the person only from the signed-in subject" | Implemented |
| T18 | Cross-site request forgery | State-changing requests need an `Origin` or `Referer` matching the configured base URL; none configured refuses them all | `tests/http.test.ts` "refuses state-changing requests from another origin" | Implemented |
| T19 | A stolen or unattended session exports the person's data or redirects their contact details | Export and contact-detail changes need a sign-in within 15 minutes; export is never cached | `tests/http.test.ts` "needs a recent sign-in" | Implemented |
| T20 | Bulk harvesting of names through the lookup endpoints | Answers gated by the disclosure context's relationships and uniform for unknown people; 60 lookups a minute per viewer, counted in the database | `tests/http.test.ts` "limits each viewer's lookups" | Implemented |
| T21 | Lost updates between tabs or devices | Changes carry the version they were made against; a stale one is refused with `conflict` | `tests/http.test.ts` "refusing a stale version" | Implemented |
| T22 | Values leaking in error responses | Errors carry codes only; validation problems as codes, never the value | `tests/http.test.ts` "validates bodies strictly" | Implemented |
| T23 | The pages show or decide more than the server allows | The pages decide nothing: they reach the server only through `useProfile()`; fields are checked with the contract's schemas and again on the server; no erasure on any page | `tests/presentation.test.ts` "reach the server only through useProfile()", "never offer erasure"; `tests/e2e/pages.spec.ts` | Implemented (phase 3) |
| T24 | Clickjacking, cached pages or leaked paths expose a person's data | Every page is sent with `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `Cache-Control: no-store` and `Referrer-Policy: no-referrer` | `tests/e2e/pages.spec.ts` "protects every page" | Implemented (phase 3) |
| T25 | Names leak through the browser: titles, history, a shared cache, or a link that reveals who exists | The person page's title is generic; display names are looked up in the browser only, per viewer, never cached on the server, kept a minute and dropped by `forgetProfileNames()`; unknown, hidden and malformed people read alike, and only disclosed names link | `tests/presentation.test.ts` "keep names out of the document title"; `tests/e2e/pages.spec.ts` "shows another person only what they disclose", "names people by what Profile discloses" | Implemented (phase 3) |
| T26 | Pages unusable by people with disabilities | WCAG 2.2 AA: axe in CI, keyboard journeys, focus on errors, reflow at 320 pixels, non-text contrast with the playground theme's real styles; colours only through the semantic vocabulary | `tests/e2e/pages.spec.ts`; `tests/presentation.test.ts` "semantic presentation" | Implemented (phase 3) |
| T27 | A suspended member's name shown to someone who need not know it | Only in an `administration` lookup for a group, by display name only and within the audience the person chose, to a viewer the host's access decision allows `profile.suspended-people:view` (declared high; the host grants it by name only, at `aal2`) on that group; asked once per lookup, only when the answer would name someone; a failure refuses the lookup | `tests/disclosure.test.ts`, `tests/http.test.ts` "names a suspended member" | Implemented (phase 4) |
| T28 | A legal hold bypassed, or used to keep data for ever | Holds are operators' only (server functions, reason code, end date at most 7 years); a hold covering Profile keeps a closed person's record readable by no function and refuses `eraseProfile`; only `profile` and parts the host declared `holdable` can be held; Profile tells the host which of its parts to keep (`profileLegalHoldParts`) and which to erase when a hold ends (`profile.legal-hold-ended`); holds end on their date in maintenance; holds, requests and closures cannot be deleted by the runtime role | `tests/database.test.ts` "keeps a closed person's record under a legal hold" | Implemented (phase 4) |
| T29 | An access archive leaks: another person, a stale session, a cache, or a partial answer taken as complete | The archive is assembled only for the person who asked, after a recent sign-in, never cached, for 7 days after completion, then deleted; each part is sealed with the person's key and dies with it; a coordinated part that failed stays pending, so no partial archive is ever offered | `tests/http.test.ts` "answers an access request", "keeps an access request open" | Implemented (phase 4) |
| T30 | Requests or holds carry personal data into events and logs | Requests, parts, holds and their events hold identifiers, codes and times only (schema-checked); groups named by opaque identifiers only; part names in a code grammar, checked by schema and database | `tests/contracts.test.ts` "records requests and holds", `tests/database.test.ts` | Implemented (phase 4) |
| T31 | A wrong or moved clock ends a hold, an archive or a code's life early, or makes an old sign-in look recent | The clock is a host-supplied trust, like the key wrapper: composed only from the host's server code (`composeProfile`'s `clock`), never from a request; the same clock for every member, or Clock's system clock; every time Profile keeps or judges comes from it, and the database is given its time rather than judging its own; an answer Clock rejects as an instant, or a failure, refuses the operation (`unavailable`) with no fallback, Clock's failures recognised as `ClockError`; day and month deadlines are calendar units in the host's `timeZone` (UTC without it) with Clock's `compatible` disambiguation, so daylight saving neither shortens nor lengthens them by an hour; a movable clock is for tests only | `tests/clock.test.ts`; `tests/composition.test.ts` "uses Clock's system clock when the host supplies none", "reckons through Clock", "fails closed on a clock that throws"; `tests/http.test.ts` "takes every time from the supplied clock", "fails closed when the clock answers an invalid time" | Implemented (phase 6) |
| T32 | A deleted group's departure records, with the names kept for its leavers, linger after the group is gone | Disposed of on `disposeProfileGroup`, which the host calls when disposal is due, confirmed with `profile.group-disposed` so that the host can raise a Profile that never confirms; the departure of a person a legal hold covers is kept | `tests/database.test.ts` | Implemented |
| T33 | Retention deletes a request a hold should keep, or the runtime role deletes records | Requests and holds are deleted only by the owner's function, past hard floors, and never a completed request of a person an active hold covers; the runtime role still has no delete on them | `tests/database.test.ts` | Implemented |
| T35 | A request or hold names a part no one answers for, settling or holding it wrongly, or a part change strands stored rows | Profile names only `profile`; every other part is declared by the host and checked at composition (unique code names, at most one directory part, defaults declared, coordinated parts need the coordination port); requests, holds and reports name only declared parts, holds only holdable ones, and the host cannot report `profile` or the directory part done; parts no longer declared still read back; migration 0006 checks the grammar, not a list | `tests/contracts.test.ts` "knows its own part only"; `tests/composition.test.ts`; `tests/database.test.ts` "accepts only the parts the host declared", "keeps part names stored before" | Implemented (phase 12) |
| T34 | Test stand-ins reach a real deployment, signing anyone in and disclosing by fiat | `createProfileTestPorts` throws unless `NODE_ENV` is `test` or the caller passes `{ demonstration: true }`; there is still no stand-in database and no default key | `tests/testing.test.ts` | Implemented |
| T16 | Supply-chain compromise | Minimal dependencies (`zod`); `minimumReleaseAge`, `blockExoticSubdeps`, frozen lockfile, dependency review | `pnpm-workspace.yaml`, workflows | Implemented |

## 4. Gaps and risk treatments

| Gap | Risk | Treatment |
|---|---|---|
| Group names on the departures page come from the host | Without the host's `ProfileGroupName` backing, the person sees "A group you left" for each | The host backs `ProfileGroupName` with its directory's names for the groups; Profile never holds group names |
| Due dates follow UK data protection | Other jurisdictions have other deadlines and exemptions | `PROFILE_REQUEST_POLICY` holds the defaults; jurisdiction packs are planned by the host |
| Parts a host does not declare | A request covers only `profile` and the declared parts | The host declares a part for each store that holds the person's data, and answers coordinated ones through its coordination port |
| One key unwrap per person per lookup | Cost and latency with a remote KMS | Host may cache unwrapped keys briefly in its wrapper; a batch port may follow |
| `createLocalProfileKeyWrapper` keeps master keys in application memory | Master keys exposed with the process | For development and self-hosting only; production should wrap through a KMS, HSM or vault |
